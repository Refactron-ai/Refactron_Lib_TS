# Plan: v0.3.0 — SQLAlchemy 1.x → 2.0 Migration

> Owner: omsherikar
> PRD / strategy: `dev-docs/Refactron_v0.3.0_SQLAlchemy_Migration.md`
> Started: 2026-06-18
> Target merge: 2026-07-30 (~6 weeks)

## Goal

Ship `sqlalchemy_query_to_select` — Refactron's first high-blast-radius transform — split into (a) a deterministic rewrite for the safe subset of `session.query(...)` chains and (b) a precondition-flag inventory for every unsafe pattern, with a **query-level test-coverage reporter** so the green-test gate means something on data-layer code.

## Architecture

Three new pieces compose around the existing engines:

1. **Detector** (`src/analyze/detectors/python/sqlalchemy-query.ts`) — tree-sitter walk; classifies every `session.query(...)`-rooted chain into one of: safe-shape, flag-shape, ambiguous-skip. Emits one finding per safe-shape chain, one precondition pre-record per flag-shape chain.
2. **Sidecar** (`src/transform/transforms/python/_py/sqlalchemy_query_to_select.py`) — LibCST visitor; for every safe-shape chain, builds the equivalent `session.execute(select(...))` chain, injects `select` / `func` imports as needed (after `from __future__` block), and rewrites in place. For every flag-shape chain, emits a precondition with id + reason and leaves bytes untouched.
3. **Coverage reporter** (`src/analyze/coverage/python-line-coverage.ts`, new module) — runs the project's test suite once with `coverage.py` instrumentation, parses `.coverage` SQLite data, returns a `Set<string>` of `<file>:<line>` keys representing executed lines. The detector cross-references each query-site line against this set; findings carry a `testCovered: boolean` field. **The 3-gate verifier consumes this field**: if the user-selected scope contains uncovered queries, verifier downgrades confidence and surfaces a coverage warning before any rewrite proceeds.

The atomic-writer, blast-radius scorer, precondition discipline, and 3-gate verifier are unchanged.

## Tech / dependencies

- TypeScript core: tree-sitter-python (existing), no new deps.
- Python sidecar: LibCST (existing, vendored expectation).
- **New dep in the user's project (NOT in Refactron itself):** `coverage.py` must be installed in the user's project for the coverage reporter to function. If absent, the reporter degrades to a "coverage unknown" mode that flags every query as `testCovered: unknown` — never silently passes.
- **No new Refactron locked-contract changes.** The new transform id `sqlalchemy_query_to_select` is an additive entry in `src/contracts.ts` `TransformId` union (additive, semver-minor compatible).
- Files locked (NONE touched in this plan): `src/contracts.ts` (additive only), `src/core/models.ts` (untouched), `src/adapters/interface.ts` (untouched).

## Phase 1 — Build the deterministic subset (Weeks 2–4)

### Week 2 — Core rewrite shapes

#### Task 1.1: LibCST chain extractor

**Files:**

- Create: `src/transform/transforms/python/_py/_sqlalchemy_chain.py` (shared helper)
- Test: `tests/unit/transform/transforms/python/sqlalchemy-chain.test.ts` (runs the helper as a Python smoke test)

The chain extractor takes a `cst.Call` node and walks left through `.func.value` attributes/calls, building a list of `(method_name, args)` tuples plus a `head_call`. Example:

```python
session.query(User).filter(User.active == True).all()
```

Extracts to:

- `head: Call(Attribute(Name('session'), 'query'), [Arg(Name('User'))])`
- `links: [('filter', [Arg(Compare(...))]), ('all', [])]`

- [ ] **Write failing test** — feed a 3-link chain, assert the extractor returns the right structure.
- [ ] **Implement minimum** — recursive walk on `cst.Call.func` when it's an `Attribute` whose `value` is itself a `Call`.
- [ ] **Verify** — every chain shape from the Phase-0 classification table extracts correctly.
- [ ] **Commit** — `feat(transform-sidecar): sqlalchemy chain extractor helper`.

#### Task 1.2: Model resolver

**Files:**

- Modify: `_sqlalchemy_chain.py` — add `resolve_model(head_call) -> Optional[cst.Name | cst.Attribute]`. Returns the model class node if the head is `query(SingleModelClass)`. Returns `None` if multi-arg, computed, or non-name (e.g. `query(User.id)`).

- [ ] **Test cases:** `query(User)` → resolves; `query(User.id)` → `None` (multi-column flag); `query(User, Address)` → `None` (multi-entity flag); `query(some_func())` → `None`.
- [ ] **Commit** — `feat(transform-sidecar): sqlalchemy model resolver`.

#### Task 1.3: `.filter()` → `.where()` and `.filter_by()` → `.where()` rewrite

**Files:**

- Modify: `_py/sqlalchemy_query_to_select.py` — first real sidecar entry. Visit `cst.Call`, extract chain, model-resolve, then for each `(method_name, args)` link, apply rewrite.

- `.filter(cond)` → `.where(cond)` is a `method_name` swap; arg passes through. Trivial.
- `.filter_by(k=v, ...)` → `.where(Model.k == v, Model.k2 == v2, ...)` requires the resolved Model to qualify column names. If Model is `None`, refuse with precondition `filter-by-without-resolvable-model`.

- [ ] **Test the happy paths.** Test the refusal — `filter_by` after a multi-arg query → precondition emitted, no rewrite.
- [ ] **Commit** — `feat(transform-sidecar): sqlalchemy filter/filter_by → where`.

#### Task 1.4: Terminal-method rewrite (`.all()` / `.first()` / `.one()` / `.one_or_none()`)

The 2.0 canonical forms (verified against `docs.sqlalchemy.org/en/20/orm/queryguide/select.html`):

| 1.x terminal     | 2.0 form                |
| ---------------- | ----------------------- |
| `.all()`         | `.scalars().all()`      |
| `.first()`       | `.scalars().first()`    |
| `.one()`         | `.scalar_one()`         |
| `.one_or_none()` | `.scalar_one_or_none()` |

Note: `.scalar_one()` (single call) is the canonical form per the SQLAlchemy 2.0 docs, NOT `.scalars().one()` (two calls). The strategic doc said `.scalars().one()`; this plan corrects to `.scalar_one()`.

- [ ] **Test each terminal.** Test that unknown terminals (e.g. `.something_custom()`) get refused with `unknown-terminal-method`.
- [ ] **Commit** — `feat(transform-sidecar): sqlalchemy terminal → scalars/scalar_one`.

### Week 3 — Wrap, get, count, imports

#### Task 1.5: `session.execute(select(...))` wrapping

The full transform sandwiches the chain. Given:

```python
users = session.query(User).filter(...).all()
```

The rewriter must produce:

```python
users = session.execute(select(User).where(...)).scalars().all()
```

Implementation: after the chain rewrite step, find the `session` reference at the head, replace `session.query(Model)` with `select(Model)`, and wrap the entire expression in `session.execute(...)`. The terminal stays at the outermost position.

- [ ] **Test the full sandwich on each terminal.** Verify the produced `cst.Call` graph round-trips through `module.code` to valid Python.
- [ ] **Commit** — `feat(transform-sidecar): wrap with session.execute(select())`.

#### Task 1.6: `session.query(Model).get(pk)` → `session.get(Model, pk)`

Different shape — terminal `.get(pk)` is not wrapped in `execute(...)`; instead the whole chain collapses to `session.get(Model, pk)`.

- [ ] **Test the rewrite.** Test composite-key refusal: `.get((a, b))` → precondition `composite-key-get`, no rewrite.
- [ ] **Commit** — `feat(transform-sidecar): sqlalchemy .get() → session.get()`.

#### Task 1.7: `.count()` → `select(func.count()).select_from(Model)` (simple shape)

The plan and the docs agree: simple `.count()` on a single-model query rewrites to `session.scalar(select(func.count()).select_from(Model))`. Anything else (count on filtered chain with joins, count on multi-column, count with distinct) → flag.

- [ ] **Test simple shape.** Test flag for `.filter(...).count()` (filtered count — semantics preserved by the rewrite but the result-shape change is non-obvious; flag for first release).
- [ ] **Commit** — `feat(transform-sidecar): sqlalchemy .count() simple-shape rewrite`.

#### Task 1.8: Import injection

**Files:**

- Modify: `_py/sqlalchemy_query_to_select.py` — at module level, after walking the visitor, inject `from sqlalchemy import select` and (if needed) `from sqlalchemy import func` after the last `from __future__` import (PEP 236 ordering — same fix as `class_to_dataclass`).

- [ ] **Test** — file without existing `select` import gets one; file with `select` already imported does not duplicate; file with `__future__` import gets the new import after it, not before.
- [ ] **Commit** — `feat(transform-sidecar): sqlalchemy import injection (post __future__)`.

### Week 4 — Flag detectors and fixture corpus

#### Task 1.9: Flag detectors (one per pattern, parallel-implementable)

Each of the flag patterns from Task 0.2 gets its full precondition record in the sidecar. The detector pre-records were stubs; the sidecar fills them in with the actual reason text. The precondition records carry these fields:

```typescript
{
  id: `sqlalchemy-query-to-select.${reason_id}`,  // e.g. 'sqlalchemy-query-to-select.lazy-dynamic'
  satisfied: false,
  reason: string,             // human-readable explanation (~1-2 sentences)
  site: { file: string, line: number },
  testCovered: 'yes' | 'no' | 'unknown',
  suggestedAction: 'manual-migration' | 'leave-as-is' | 'consult-sqlalchemy-2.0-guide',
  migrationGuideAnchor?: string,  // link into docs.sqlalchemy.org/en/20/changelog/migration_20.html
}
```

| Reason id                 | Human-readable reason                                                                                                                                                                                    |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lazy-dynamic`            | Relationship uses `lazy="dynamic"`, which remains Query-based in SQLAlchemy 2.0 and is documented as legacy. Migrate to `lazy="write_only"` by hand.                                                     |
| `multi-column-select`     | Query selects multiple columns (`query(Model.id, Model.name)`) — `.scalars()` would be wrong; result-shape access pattern depends on caller.                                                             |
| `multi-statement-chain`   | Query is built across multiple statements with conditional `.filter()` appends — auto-rewrite cannot prove the assembled WHERE is equivalent.                                                            |
| `joinedload-needs-unique` | `joinedload(...)` in the chain — SQLAlchemy 2.0 does NOT deduplicate joined-eager results by default; the rewrite would require `.unique()` to preserve behavior. Migrate by hand and decide explicitly. |
| `bulk-update-semantics`   | `Query.update()` bulk semantics changed in 2.0 (`synchronize_session` default is now `'auto'`). Manual migration.                                                                                        |
| `bulk-delete-semantics`   | `Query.delete()` bulk semantics changed in 2.0. Manual migration.                                                                                                                                        |
| `select-entity-from`      | `Query.select_entity_from()` is a 1.x-only construct with no direct 2.0 equivalent. Manual migration.                                                                                                    |
| `complex-joins`           | Chain contains 3+ chained joins or self-referential joins — rewrite cannot prove join-clause ordering preserves results.                                                                                 |
| `composite-key-get`       | `.get((a, b))` — composite primary key; `session.get(Model, (a, b))` is the 2.0 form but the tuple shape may need adjustment. Manual review.                                                             |
| `unknown-terminal-method` | Terminal method is not in the known map. Refusing to guess the 2.0 equivalent.                                                                                                                           |

- [ ] Each row gets a sidecar branch and a unit test. ~10 commits expected, all small and parallelizable.

## Out of scope (deferred to v0.4 or later)

Tracked separately so they don't grow the v0.3.0 surface:

- [ ] Core-style `engine.execute()` migration (separate transform — `sqlalchemy_engine_execute_to_session`).
- [ ] Alembic migration scripts (`env.py` patterns differ from app code).
- [ ] Async (`AsyncSession`) specifics.
- [ ] `Query` API removal in SQLAlchemy 2.1+ (not yet shipped; track when 2.1 RC lands).
- [ ] `declarative_base()` → `class Base(DeclarativeBase)` rewrite (related but separate transform).
- [ ] `lazy="dynamic"` → `lazy="write_only"` automated rewrite (still flagged this release; auto-rewrite once 2.0 patterns stabilize).
- [ ] Rewriting the `.unique()` insertion for `joinedload` — flagged this release; auto-rewrite once we have confidence the semantic change is OK to apply.
- [ ] Bulk update/delete rewrite (flagged this release; auto-rewrite when `synchronize_session='auto'` semantics are widely understood).

Each of these is an issue to file before v0.3.0 ships, so the deferral is tracked.

## Risks & mitigations

| Risk                                                   | Likelihood | Impact                                             | Mitigation                                                                                   |
| ------------------------------------------------------ | ---------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Test coverage on real codebases is too thin → G0 fails | Medium     | Existential                                        | Phase 0 exists exactly for this; pivot to flag-only release if G0 fails.                     |
| Safe subset < 20% of real query surface                | Medium     | Reduces value of auto-rewrite                      | Flag-only release is still valuable; pivot framing to "migration planner."                   |
| `coverage.py` adoption is low in target codebases      | Medium     | Coverage reporter returns `unknown` for most sites | Document the dependency clearly. Degraded mode still ships the flag inventory.               |

## Open questions (resolve before Phase 1)

1. **Coverage threshold for G0** — provisional ≥50%. Final number lives in the Phase 0 report. Below 25% means stop; between 25–50% means ship as flag-only with no auto-rewrite.
2. **Canonical 2.0 form for `.all()`** — `session.scalars(select(...)).all()` (the 1-call shortcut) vs `session.execute(select(...)).scalars().all()` (the explicit form). Both are valid; the docs use both. **Decision needed**: pick one for consistency, document, never mix. **Proposed default**: the explicit form, because it's the shape closest to the user's mental model of the change.
3. **`.count()` rewrite form** — `select(func.count()).select_from(Model)` vs `select(func.count(Model.id))`. Both valid. **Proposed default**: `select(func.count()).select_from(Model)`, because it matches the strategic doc's example.
4. **Should the coverage reporter be a separate v0.2.5 release** so v0.3.0 ships pure-transform? Argument for: separates concerns and de-risks v0.3.0. Argument against: the coverage reporter is the thing that makes the SQLAlchemy transform safe; shipping the transform without it is shipping fake-verified rewrites. **Recommendation**: bundle into v0.3.0; the dependency is fundamental.

## What this plan deliberately is NOT

- Not a roadmap for v0.3.x or v0.4. Other improvements (the 8 transform candidates filed as #62–#69) wait.
- Not a release-vehicle for unrelated fixes. v0.3.0 is one transform, on purpose.
- Not a claim that we ship "verified" without the coverage report.
- Not a skip of Phase 0. The premise gets validated before the rewrites get built.
