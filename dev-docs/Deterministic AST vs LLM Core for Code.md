# Deterministic AST vs LLM Core for Code Modernization in 2025-2026: A Strategic Intelligence Report

## TL;DR

- **The dominant production architecture across large MNCs and Tier-1 consultancies in 2025-2026 is hybrid, not pure-LLM.** The overwhelming majority of named programs use a deterministic AST/codemod core (or rule-based engine) to PRODUCE the actual code change, with LLMs confined to the periphery: understanding, business-rule extraction, summarization, documentation, test scaffolding, and target identification. Even self-described "LLM-core" systems (Amazon Q Code Transformation, IBM watsonx Code Assistant for Z, Mechanical Orchard Imogen, Cognition Devin) are wrapped in deterministic verification gates (compilers, tests, behavioral equivalence checks).
- **The empirical and peer-reviewed evidence in 2024-2026 is actively unfavorable to LLM-only code transformation.** METR's RCT (Becker, Rush, Barnes, Rein, arXiv:2507.09089) found a 19% slowdown for experienced developers using Cursor Pro with Claude 3.5/3.7 Sonnet on their own repositories; the Spracklen et al. slopsquatting paper (arXiv:2406.10279) documented a 19.7% package hallucination rate across 16 leading code-gen LLMs (21.7% open-source, 5.2% commercial); the NYU "Asleep at the Keyboard" study (Pearce et al., IEEE S&P 2022) found 39.33% of Copilot's top suggestions vulnerable across 1,689 generated programs; GitClear's 211M-LOC 2025 analysis showed code churn doubling and an 8x rise in cloned code blocks since Copilot's mainstream adoption.
- **A "deterministic core + LLM periphery (only for documentation)" architecture is directly aligned with the majority position of every credible technical authority** (Thoughtworks Technology Radar Vol. 32-34, Gartner, Moderne/OpenRewrite, Meta, Uber, Instagram, Airbnb, Google, Cognizant, HCLTech), but the market is not static: Capgemini's May 2025 mainframe offering, McKinsey's LegacyX, BCG X's multi-agent framework, and the agentic-core camp (Devin, Amp, Claude Code, Imogen) are openly pushing LLM-forward architectures. The bet is currently correct on technical merits; the open question is whether continued model improvement and per-recipe authoring cost shift the equilibrium by 2027-2028.

## Key Findings

1. **Deterministic AST tooling is the documented core engine at Meta (CodemodService, SCARF), Uber (Polyglot Piranha), Instagram (LibCST), Airbnb (ts-migrate), Google (pasta), and is the technology AWS itself uses inside Amazon Q Code Transformation** for the Java upgrade step (Moderne/OpenRewrite is named in the AWS launch blog as a component of the service). This is verified from each company's own engineering blog, source code, and press releases, not from analyst commentary.
2. **LLM-core systems all internally depend on deterministic infrastructure.** Amazon Q uses Maven/Gradle build verification and OpenRewrite recipes; IBM watsonx Code Assistant for Z (WCA4Z) pipelines Application Discovery and Delivery Intelligence (ADDI) static analysis → Refactoring Assistant extraction → Granite LLM → Validate test gates; Mechanical Orchard Imogen captures "actual data flows across component interfaces" as a behavioral specification and verifies AI-generated code against it; Devin's reported SWE-bench gains depend on the deterministic unit-test harness.
3. **Peer-reviewed evidence is converging on the limits of LLM-as-core.** Devin self-reported 13.86% resolution on a 25% SWE-bench subset; package hallucination is "a systemic and persistent phenomenon" across all 16 LLMs tested; and the METR RCT found experienced developers were slowed 19% even with expert-level Cursor/Claude familiarity (with the study's own February 2026 follow-up unable to reproduce a clean signal due to study attrition).
4. **Consultancy positioning splits cleanly along the deterministic-vs-LLM-core axis.** Thoughtworks, Gartner, HCLTech, Cognizant, TCS, Wipro, and Infosys publicly favor deterministic-core or deterministic-primary hybrids; Capgemini's May 2025 launch, McKinsey LegacyX (QuantumBlack), and BCG X are explicitly LLM/agentic-core; Forrester observes the market is in transition. Deloitte's joint work with NVIDIA documents LLM "token drift" as "an unacceptable level of risk" for code generation.
5. **Regulatory tailwinds favor deterministic in financial services, healthcare, and government.** Deloitte's published position, Gartner's "Predicts 2026" note, and TCS's BFSI architect blog all flag LLM non-determinism as a compliance problem for audit-trail-bound industries.

## Section A: Why Deterministic AST is Preferred as Core

### A.1 The named MNC programs that use deterministic AST as the core

The evidence for deterministic-core in production at large MNCs is unusually strong because each company has published either source code, an engineering blog, or both:

- **Meta — CodemodService + SCARF.** Meta's October 2023 engineering blog states: *"SCARF was the first instance of company-wide, fully automated code changes at Meta, and was built hand-in-hand alongside CodemodService. Today, CodemodService also powers hundreds of other types of automated code changes at Meta, from automating the formatting of code, automatically removing completed experiments, empowering large-scale API migrations, to improving coverage of strong types in partially-typed languages like Python and Hack."* SCARF combines static and dynamic program analysis to identify dead code, then dispatches deterministic codemod-driven removals via CodemodService — no LLM in the change-producing loop.
- **Uber — Polyglot Piranha (PiranhaJava on Error Prone, PiranhaSwift on SwiftSyntax, PiranhaObjC as a Clang plugin).** Uber's ICSE-SEIP 2020 paper reports ~200 developers used Piranha to delete 1,381 stale feature flags spanning 71 KLOC, with 65% of generated cleanup diffs landing without manual changes. The Java diffs were ~71% CI-clean and Objective-C diffs ~99% — itself a justification for keeping the transformation rule-based and reviewable. A PLDI 2024 paper updates the Polyglot Piranha generalization.
- **Instagram — LibCST.** Their "Static Analysis at Scale: An Instagram Story" blog documents linting and automated refactoring of one of the world's largest Python codebases using LibCST's lossless concrete syntax tree, specifically chosen because *"It provides a lossless representation like a concrete syntax tree (CST), but still makes it easy to extract semantics like an abstract syntax tree (AST)."*
- **Airbnb — ts-migrate.** Airbnb's engineering Medium post and the open-source repo (airbnb/ts-migrate) describe the JavaScript-to-TypeScript migration tool: *"We were able to convert projects with more than 50,000 lines of code and 1,000+ files from JavaScript to TypeScript in one day with the use of codemods!"* Airbnb has converted approximately 86% of its 6M-line frontend monorepo entirely via deterministic AST-based plugins, not LLMs.
- **Google — pasta.** A public open-source AST-based Python refactoring library with the explicit symmetry guarantee `pasta.dump(pasta.parse(src)) == src`.
- **AWS — chose OpenRewrite as a component of Amazon Q Code Transformation.** Moderne CEO Jonathan Schneider's quote in the AWS launch blog: *"we're excited to see AWS using OpenRewrite, the open source automated code refactoring technology, as a component of their service."* This is the most strategically revealing fact in the corpus: the leading LLM-marketed transform service is in fact OpenRewrite-backed for its actual Java step.
- **SeatGeek, Instawork, Reddit, Indeed, Workiva** — all publicly use LibCST or Sourcegraph Batch Changes for production codemods (each documented in their own engineering posts).

### A.2 Specific technical arguments documented in primary sources

OpenRewrite/Moderne's own documentation gives the clearest articulated argument set:

- **Lossless Semantic Trees (LST), not bare ASTs.** From Moderne in InfoWorld: *"Most automated refactoring tools work with basic text patterns or Abstract Syntax Trees (ASTs). ASTs are the backbone of compilers, but they're not designed for modernization. They strip out comments, whitespace, and formatting, and they don't resolve method overloads, generics, or dependencies across classpaths. They give you what the code says, not what it means."* LSTs preserve comments, whitespace, and type-attributed dependencies, making diffs human-reviewable.
- **Determinism, reproducibility, auditability.** Moderne's myth-busting post: *"OpenRewrite recipes are deterministic and don't rely on AI for decision-making, so you always know what changes are being made... Most recipes are human-authored... and make the same predictable change every time they run."*
- **Type-attributed transforms catch breaking changes at compile time.** Moderne's October 2025 announcement of JS/TS LST support frames it as *"the first truly compiler-accurate, type-aware refactoring engine, moving beyond syntax-bound codemods to enable safe, large-scale upgrades and program analysis."*
- **Provable termination, CI/CD integration, exit codes.** OpenRewrite recipes are testable, composable, and run under `mvn rewrite:run` / `gradle rewriteRun`, producing diffs reviewable line-by-line.
- **Scale without context-window issues.** Moderne batch-builds LSTs once and serializes them, so the same LST can be queried by *"agents [that] work with less token overhead and more accuracy than they would reading a codebase file by file."*

The canonical academic chain (Opdyke 1992, Roberts 1999, Mens & Tourwé 2002, Fowler) underpins the precondition-based behavior-preservation guarantee that AST/LST tools attempt to honor. The AlOmar, Mkaouer, Newman, Ouni 2021 systematic mapping study (arXiv:2106.13900) catalogs behavior-preservation strategies in refactoring and notes the research bias toward "precondition-based and testing-based approaches", exactly the architecture deterministic tools implement.

### A.3 Thoughtworks Technology Radar position

The Thoughtworks Technology Radar (Vol. 32 April 2025, Vol. 33 Nov 2025, Vol. 34 April 2026) places OpenRewrite in the **Trial** ring with the explicit comparison: *"Using an AI coding assistant is an alternative, but for rule-based changes, it's usually slower, more expensive and less reliable."* The Vol. 33 "AI for code migrations" technique entry: *"Using AI alone for such upgrades has often proven costly and prone to meandering conversations. Instead, the team combined traditional upgrade pipelines with agentic coding assistants to manage complex transitions. Rather than delegating a full upgrade, they broke the process into smaller, verifiable steps: analyzing compilation errors, generating migration diffs and validating tests iteratively."* Vol. 34 generalizes this into the "feedback sensors for coding agents" technique: *"deterministic quality gates, compilers, linters, type checkers and test suites, integrated directly into agent workflows so failures trigger auto-correction before human review."*

### A.4 Documented limits of deterministic approaches

The deterministic camp has been honest about its limitations:
- **Per-recipe authoring cost is high.** Each Piranha language variant (Java/Swift/Objective-C) required a separate implementation; ts-migrate plugins are language- and framework-specific.
- **Brittle to non-canonical formatting** unless the parser supports the format. LibCST addresses this by being lossless; jscodeshift and bare AST tools are notably weaker.
- **Cannot do semantic-equivalence rewrites** (different control flow producing the same output) without explicit pattern enumeration.
- **Multi-file and cross-language refactorings require language-specific parsers** per language pair.
- **Land rates fall on harder languages.** Uber's own paper showed PiranhaObjC diffs were ~99% CI-clean while PiranhaJava was ~71%, i.e. deterministic tools degrade as language semantics get richer.

## Section B: Why LLMs are Preferred as Core (Where They Are)

### B.1 The named programs that genuinely use LLMs as the change-producing core

- **Amazon Q Code Transformation / Q Developer Transform.** Extended at re:Invent 2024 to Windows .NET, VMware, and mainframe modernization. AWS press release: *"Earlier this year, Amazon integrated the Java transformation capability of Amazon Q Developer into its internal systems to migrate tens of thousands of production applications from older versions of Java to Java 17."* However, the actual Java upgrade step uses OpenRewrite recipes; the LLM orchestrates planning and dependency resolution while the deterministic engine performs the structural change. AWS Transform (custom) was added in 2025 with agentic AI for version upgrades.
- **IBM watsonx Code Assistant for Z (WCA4Z).** Trained on a Granite LLM (initially 20B parameters, learning from 1.5T tokens across 115 coding languages). Accenture's pipeline explainer is unusually clear: ADDI (static analysis) → Refactoring Assistant (extraction) → Granite LLM → Validate (tests). The 2.8 release in 2025 added MCP-enabled agentic tools where deterministic static analysis ("Z Understand Metadata Retrieval", "Impact Analysis") feeds the LLM.
- **Mechanical Orchard — Imogen.** Their architecture is explicitly LLM-core with deterministic verification: *"Imogen captures what a system actually does, through real data flows across component interfaces, and uses that behavioral specification to guide AI code generation and prove equivalence at every step."* Their April 2025 reflections post: *"Generative AI has made it practical, and cost-effective, to execute on the gold standard of mainframe migration: incrementally rewriting an exact functional and behavioral replica into modern code."* Thoughtworks is their announced first partner.
- **Cognition Devin.** Self-reported 13.86% SWE-bench resolution rate at launch (570-issue 25% subset). According to OpenAIToolsHub's April 2026 commercial review (a vendor-review site, not an independent research body), *"Independent evaluations and community reports consistently suggest Devin successfully completes approximately 14–15% of complex real-world tasks autonomously without correction"* — i.e. an ~85% effective fail rate on complex tasks, though the underlying evidence is Trustpilot reviews rather than peer-reviewed study. Third-party reporting indicates Devin's PR merge rate improved to 67% over 18 months, with Cognition's own internal application seeing roughly one-third of commits from the agent.
- **GitHub Copilot Workspace, Copilot App Modernization for Java/.NET.**
- **Sourcegraph Cody / Amp.**
- **Cursor, Claude Code, Codeium Cascade, Tabnine, SWE-agent/OpenDevin** — agentic LLM-core tools used primarily in IDE-assist rather than batch transformation.

### B.2 The technical arguments for LLM-core

The honest arguments, extracted from the IBM, Amazon, and Mechanical Orchard documentation:

- **Handles non-canonical, undocumented, or poorly-formatted legacy code** where deterministic parsers struggle (especially when copybooks, JCL, and screen definitions interleave with COBOL).
- **Cross-language semantic translation** (COBOL → Java, PHP → TypeScript) where there is no clean rule-based mapping.
- **Can generate missing tests, documentation, and explanations during migration** (this is precisely the periphery use case where the deterministic camp also adopts LLMs).
- **Lower per-migration authoring cost** because no recipe is written; a model handles many migration shapes.
- **Understands natural-language intent** from comments and variable names.

### B.3 The honest, peer-reviewed failure data

The LLM-core position must reckon with a growing body of unfavorable empirical evidence:

- **Package hallucination at 19.7% (Spracklen et al., arXiv:2406.10279, 2024-2025).** Across 16 LLMs and 576,000 code samples in Python and JavaScript, 19.7% of generated package references were hallucinations, including 205,474 unique non-existent package names. Open-source models averaged 21.7% hallucination; commercial models 5.2%. CodeLlama 7B and CodeLlama 34B hallucinated in over a third of outputs. The authors describe this as *"a systemic and persistent phenomenon."* This is the foundation of the "slopsquatting" supply-chain attack class.
- **NYU "Asleep at the Keyboard" (Pearce, Ahmad, Tan, Dolan-Gavitt, Karri, IEEE S&P 2022, arXiv:2108.09293).** Of 1,689 programs generated by Copilot across 89 MITRE CWE-relevant scenarios, *"approximately 40% to be vulnerable"*; specifically 39.33% of top suggestions were vulnerable. The paper received a Distinguished Paper Award at IEEE S&P 2022.
- **METR RCT (Becker, Rush, Barnes, Rein, arXiv:2507.09089, July 2025).** 16 experienced open-source developers; 246 tasks on their own repositories, conducted February-June 2025, with random AI-allowed/AI-disallowed assignment. Developers used Cursor Pro with Claude 3.5/3.7 Sonnet. *"When developers are allowed to use AI tools, they take 19% longer to complete issues."* Developers themselves predicted a 24% speed-up and reported a 20% speed-up after experiencing the slowdown. METR's February 2026 follow-up post acknowledges the original cohort still shows -18% (slowdown) while newer cohorts show -4%, but with study attrition and a halved pay rate ($150/hr → $50/hr) creating selection effects.
- **GitClear "Coding on Copilot" (2024, 153M LOC) and AI Copilot Code Quality (2025, 211M LOC).** Code churn (lines reverted within two weeks) doubled from the 2021 pre-AI baseline (3.1% → projected 5.7-7.9% in 2024); cloned code blocks increased 8x in 2024; the proportion of "moved" (refactoring) lines fell from 24.1% in 2020 to 9.5% in 2024. 2024 was the first year where introduction of repeated code exceeded refactoring activity.
- **Devin SWE-bench.** 13.86% resolution on the 570-issue 25% sample. The Cognition team's own report concedes: *"In tasks that it failed, 95 had more than 1 file changed and 230 had more than 15 lines changed. In contrast to the tasks it successfully completed 11 had more than 1 file changed and 18 had more than 15 lines changed."* That is, Devin is materially worse on multi-file changes, which is exactly the regime of code modernization.

### B.4 What the LLM camp cannot guarantee

- **No reproducibility.** Even at temperature=0, Deloitte and NVIDIA documented that *"Even when configured for deterministic behavior, LLMs could produce different outputs on the same prompt. In use cases like SQL code generation or named-entity recognition (NER), where a single token represents the only correct answer, this 'token drift' meant unpredictable and inaccurate outcomes. For financial workflows, data pipelines, or code generation, this is an unacceptable level of risk."* They trace the cause to floating-point arithmetic in GPU kernels.
- **No proof of behavior preservation** other than empirical test pass rates.
- **No guaranteed termination.**
- **Scaling cost is per-LOC, not per-recipe.** A 50M-LOC enterprise modernization with a deterministic recipe pays the authoring cost once; with LLM-core it pays inference cost per file.
- **Context-window limitations** on million-LOC codebases force chunking, which is where most multi-file errors enter.

## Section C: The Hybrid Architecture Taxonomy

Four distinguishable patterns dominate 2025-2026 production deployments:

**Pattern 1: Deterministic core + LLM periphery.** Used by Meta (CodemodService + LLMs for understanding), Moderne (Moddy agent layered over OpenRewrite recipes as deterministic tool calls), Sourcegraph Batch Changes (deterministic rewrite, LLM-assisted search). Moderne explicitly: *"AI can also accelerate the authoring of recipes themselves, reducing the time from idea to working automation. That's a safer application of AI than making the changes directly, because recipes are deterministic, easily testable, and reusable across repos."*

**Pattern 2: LLM core + deterministic verification.** Devin + SWE-bench unit tests, Amazon Q Code Transformation + Maven build gates, IBM WCA4Z + validation, Mechanical Orchard Imogen + behavioral data-flow equivalence. The defining characteristic: the LLM produces the candidate change but a deterministic system (compiler, tests, replay harness) accepts or rejects it.

**Pattern 3: LLM for first-pass translation, deterministic for refinement.** Most COBOL → Java pipelines (IBM WCA4Z, Capgemini, BCG public-sector cases) use this. The LLM generates the candidate Java; rule-based cleanup (idiomatic Java, dependency injection, naming conventions) is applied by a deterministic engine.

**Pattern 4: Deterministic for the 80%, LLM for the long tail.** Recipe coverage is high for canonical patterns; LLMs fill the gaps where formatting or semantic variance exceeds the recipe author's anticipation. Thoughtworks Radar Vol. 33 documents this on a .NET upgrade: *"In the past, we blipped OpenRewrite, a deterministic, rule-based refactoring tool... the team combined traditional upgrade pipelines with agentic coding assistants to manage complex transitions. Rather than delegating a full upgrade, they broke the process into smaller, verifiable steps: analyzing compilation errors, generating migration diffs and validating tests iteratively."*

## Section F: Regulatory and Compliance Considerations

The regulatory case for deterministic-core is strongest in regulated industries:

- **Financial services (OCC, FFIEC, DORA in EU).** Auditable change trails and reproducibility are explicit requirements. Deloitte's NVIDIA piece directly: *"For financial workflows, data pipelines, or code generation, this is an unacceptable level of risk."* TCS's own BFSI architect flags this. The Digital Operational Resilience Act (DORA) requires demonstrable ICT change management for EU financial entities.
- **Healthcare (HIPAA, FDA 21 CFR Part 11).** Software-as-medical-device traceability requires each change be linkable to a deterministic origin.
- **EU AI Act.** Code generation used in regulated processes is increasingly subject to risk classification; non-deterministic outputs that cannot be reproduced are an audit liability.
- **US government (DOGE, IRS).** Public reporting suggests aggressive LLM use in modernization; multiple expert commentators have flagged this as risk-accumulating.

Gartner's "Predicts 2026" frames this organizational dimension: *"Success requires clarity in human-AI collaboration, as well as organizational readiness for agentic AI."*

## Section G: Synthesis — When to Use Which

The evidence supports a fairly clean decision framework:

- **Use deterministic-core when:** The transformation is rule-based and recurring; the codebase is large (>1M LOC); the language has rich type information (Java, Kotlin, TypeScript, C#); audit trail and reproducibility matter; the target is a framework or LTS upgrade (Spring Boot, JDK, Angular, Node); the team can amortize recipe-authoring cost over many repos.
- **Use LLM-core (with deterministic verification gates) when:** The source is poorly documented legacy code (COBOL, PL/I, older Smalltalk) with no clean grammar; the transformation requires semantic understanding of business rules; tests and documentation must be generated alongside; the migration is one-off or low-volume; behavioral equivalence can be empirically verified against running production data flows (Mechanical Orchard's model).
- **Use hybrid Pattern 1 (deterministic core + LLM periphery) when:** You want the best of both, bounded recipe coverage for the 80%, LLM for documentation, understanding, recipe-authoring assistance, and edge-case fill-in. This is the dominant enterprise default and is aligned with Meta, Moderne, Cognizant, HCLTech, Thoughtworks Radar, and Gartner's analyst position.
- **Use hybrid Pattern 2 (LLM core + deterministic verification) when:** You have access to a strong behavioral specification (production data, comprehensive test suites) and the source language is hard to parse rule-based. Mechanical Orchard's Imogen demonstrates this works in practice but requires the customer to expose real data flows.

A "deterministic core + LLM only for documentation" bet is technically aligned with: every major engineering-blog-documented MNC production deployment except Mechanical Orchard; the Thoughtworks Technology Radar position from Vol. 32 through Vol. 34; Gartner's analyst guidance (Brasier, "Predicts 2026"); Moderne/OpenRewrite's roadmap; Meta, Uber, Instagram, Airbnb, Google, AWS (via OpenRewrite), Sourcegraph; and the cautious end of the consultancy market (HCLTech, Cognizant, TCS, Infosys, Wipro, Thoughtworks).

It is misaligned with the most aggressive LLM-forward positions of Capgemini, McKinsey LegacyX, BCG X, Mechanical Orchard, and Cognition Devin.

## Section H: Predictions for 2026-2028

## Recommendations

For a vendor building a deterministic refactoring tool with LLM periphery (the "Refactron-style" architecture), the evidence supports a staged commitment:

1. **Stay deterministic-core for the actual code change.** The METR, GitClear, Spracklen, and Pearce evidence base, plus the consistent positions of Gartner, Thoughtworks, HCLTech, Cognizant, TCS, Wipro, and Infosys, all converge on this. The marginal cost of adopting an LLM-core architecture today is paying for hallucination, churn, and reproducibility loss without a defensible audit trail. Threshold to re-evaluate: a peer-reviewed RCT showing experienced developers materially faster (>10% net) on multi-file modernization tasks with LLM-core tools, and package hallucination rates below 2% on commercial models.
2. **Broaden the LLM periphery aggressively beyond documentation.** Three high-value, low-risk extensions match what Moderne (Moddy, Prethink, Trigrep, MCP server), Meta (LLMs for understanding alongside CodemodService), and Cognizant ("AI enhancing insight while deterministic systems guarantee outcomes") have already adopted: (a) AI-assisted recipe authoring, (b) business-rule and intent extraction from legacy comments, (c) target identification (telling the deterministic engine which call sites or files to touch). Threshold to expand further: customer demand for first-pass translation in cross-language migrations (which is when Pattern 3 becomes necessary).
3. **Invest in MCP-style integration with LLM agents that USE your deterministic recipes as tools.** This is Moderne's strategic positioning and Microsoft's positioning around GitHub Copilot. The endgame is that LLM agents become the user interface; the deterministic engine becomes the structural change executor. A "deterministic engine that no LLM can call" is at risk of being routed around within 18-24 months.
4. **Build the audit/compliance story explicitly.** Deloitte's NVIDIA "token drift" paper, DORA, and the EU AI Act create a regulated-industry moat for deterministic tools. Threshold to monetize: at least one banking, insurance, or healthcare customer publicly citing the deterministic audit trail as a procurement reason.
5. **Pick a small set of cross-language Pattern 3 use cases to validate hybrid LLM-translation + deterministic-refinement.** Watch IBM WCA4Z and Mechanical Orchard closely; if their behavioral-equivalence claims hold across multiple customers by 2027, the LLM-translation regime will be the growth segment.

Predictions for 2026-2028, in priority order:

1. **The hybrid architecture wins the next two years, with Pattern 1 (deterministic core + LLM periphery) being the dominant enterprise default by end-2027.** Every credible analyst (Gartner, Forrester, Thoughtworks) and every Tier-1 SI with a serious deterministic asset (TCS, HCLTech, Wipro, Infosys, Cognizant) is converging on this. Moderne's "Moddy" agentic interface over OpenRewrite recipes is the most concrete reference architecture.
2. **LLM-core systems retain a strong niche in mainframe COBOL/PL/I → Java/Python work** where deterministic grammars are weaker and behavioral specification is empirically tractable. IBM WCA4Z, Mechanical Orchard Imogen, and Capgemini's gen-AI mainframe offering will grow here. But this is a bounded market, not the general modernization market.
3. **The "AI-Augmented Code Modernization Tools" category Gartner has formalized in 2026 will become the default RFP category**, with both deterministic-core and LLM-core vendors forced to bundle the opposite capability to win deals.
4. **Determinism becomes a regulatory requirement, not a preference, in financial services and healthcare** under DORA, the EU AI Act, and OCC guidance. Deloitte's NVIDIA piece is the canary; expect formal supervisory guidance by 2027.
5. **The METR / GitClear / Spracklen empirical evidence base will harden** if the next generation of models does not deliver on hallucination rates. METR's February 2026 follow-up paper acknowledges difficulty in finding willing AI-disallowed participants, but the underlying productivity gap is unlikely to flip to materially positive without a step change in model capability.
6. **Deterministic vendors that fail to integrate LLM-driven recipe authoring, business-rule extraction, and MCP-style agent toolcall interfaces by end-2026 will be routed around.** Moderne is already building this; vendors that wait risk being treated as a backend by a competing UX layer.

## Caveats

- Many of the most strategically important documents are paywalled (Gartner Magic Quadrant, Forrester Wave full reports). Quotes used here are from press releases, analyst blogs, public excerpts, or vendor recap summaries.
- Vendor-published numbers (Capgemini's "paradigm shift", McKinsey's "40-50% acceleration", TCS's "70% cost reduction", BCG's "225x faster", Infosys's "50-70% reduction") are marketing claims, not independently verified.
- Devin's public benchmarks are self-reported and use a 25% SWE-bench subset. Independent reproductions are limited; the "~85% real-world fail rate" cited above derives from a commercial review aggregator (OpenAIToolsHub) using Trustpilot data, not a peer-reviewed study.
- The METR study used 16 developers and 246 tasks: statistically powerful given within-subject design but not enormous in absolute terms. The February 2026 follow-up flags real methodological difficulty including a halved pay rate ($150/hr → $50/hr) creating selection effects.
- "Engineering blog" evidence (Meta, Uber, Instagram, Airbnb) tells us what those companies built but not always what proportion of their actual transformation work runs through these tools today versus other channels.
- Mechanical Orchard's "behavioral equivalence" claim is, on the published evidence, equivalence against the data flows they capture; this may not exhaust the production behavior space.
- The Forrester Wave Q1 2025 "slow burn" quote is from Bill Martorelli's introduction to the App Modernization & Multicloud Managed Services Wave (March 2025), not from Diego Lo Giudice (who authored the separate Modern Application Development Services Wave Q1 2025, published January 15, 2025). The two reports differ in scope.
- Peng, Kalliamvakou, Cihon, Demirer (arXiv:2302.06590, 2022) was authored by GitHub and MIT researchers; the 55.8% speedup figure is for a controlled greenfield JavaScript task and does not transfer directly to modernization work.
