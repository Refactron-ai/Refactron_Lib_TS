## Interpretation

The 0% is not a bug in the trial driver — I verified end-to-end:

1. **Coverage reporter works** — `reportCoverage()` returned `coveredLines.size = 2,870` lines for flask-appbuilder, sourced from a real `coverage run -m pytest -q` execution inside the sandbox.
2. **Path normalization is correct** — both producer (`coverage.json` keys like `flask_appbuilder/__init__.py:1`) and consumer (detector key lookup of `flask_appbuilder/__init__.py:42`) agree on canonical form after the `fix(analyze): normalize covered-line keys` commit on this branch.
3. **The mismatch is real** — every finding the detector returned in flask-appbuilder has `file` under `bin/` or `examples/`. Sample: `bin/hash_db_password.py:33`, `examples/crud_rest_api/testdata.py:23`, `examples/employees/app/views.py:11`. The tested package (`flask_appbuilder/`) returned **zero** findings.

So the honest reading: **flask-appbuilder's SQLAlchemy 1.x patterns live in utility scripts and demo applications that have no test coverage.** The production `flask_appbuilder/` package — which is what's tested — does not contain any patterns the current detector matches.

A meaningful caveat: see "Detector blind spot" below.

## Detector blind spot (NOT a bug — a Phase 1 scope question)

Flask-SQLAlchemy idiomatic queries take the form `Model.query.filter(...).all()`, where `Model.query` is a **class attribute** (a `Query` descriptor), NOT a `.query()` method call. The current `sqlalchemy-query` detector's `walkChain` terminates when it reaches a non-call receiver, so `Model.query.filter(...).all()` is never identified as a query chain.

This means the detector counts only `session.query(...)` and `db.session.query(...)` style — the Core/SQLAlchemy-ORM session form. It misses the Flask-SQLAlchemy convenience form entirely.

The trial's 199 flask-appbuilder findings are all `session.query(...)` (or attribute-receiver equivalents); the actually-dominant `Model.query.filter(...)` pattern was zero-matched by the detector. **Even with the detector blind spot fixed, those sites would also live in `flask_appbuilder/`'s utility paths** — Flask-AppBuilder's tested code uses higher-level abstractions (declarative interface, generic views) that don't expose raw queries.

The blind spot is real and worth fixing in Phase 1 (small detector extension — handle `<Name>.query.<method>(...)` chains where `.query` is an attribute access). But it does not change the G0 verdict for this corpus.

**Status as of 2026-06-19:** resolved. See the Phase 0 redo section below.

## sqlalchemy-utils observation

128 findings, all uncovered. `sqlalchemy-utils` is a utility library, not a typical application — most of its query patterns appear in `tests/` and `sqlalchemy_utils/` modules whose tests use database fixtures that don't carry through to `coverage run`'s default collection. Same outcome as flask-appbuilder for different reasons.

## G0 Decision

**STOP — at the strategy doc's threshold reading.**

Auto-rewriting any of the 227 safe-subset sites would ship a transform whose verification (3-gate test pass) carries **zero** evidence. Per the strategy doc §0:

> "If a user's tests don't exercise the queries being rewritten, Refactron's verification gate passes a rewrite that is silently wrong — the exact failure this whole company is supposed to prevent."

## Recommended pivot (per strategy doc §0's STOP-arm options)

Two valid pivots:

### Pivot A — Ship as a detect-and-flag-only "migration planner" (Refactron's most honest move)

Drop the rewriter half from v0.3.0 entirely. Ship Phase 1 Tasks 5–17 as **detection + structured flag inventory only**. Refactron becomes "the SQLAlchemy 2.0 migration planner that tells you exactly which sites are safe and which need hand-migration, with reasoning." Strategy doc §0 explicitly endorses this: *"shipping a flag-only release is still valuable — the inventory is the bigger initial value."*

The flag inventory we ALREADY have (100 flag-subset findings across these 2 codebases, with `multi-column-select`/`bulk-delete-semantics`/`joinedload-needs-unique` breakdowns) is the artifact this release would package. The positioning becomes:

> "Refactron tells you exactly which of your SQLAlchemy 1.x queries you can safely migrate by hand and which need human review — with the reason inline. No tool gives you this today. We don't rewrite anything until your tests reach the queries."

### Pivot B — Pick a different flagship migration

If the SQLAlchemy positioning is too valuable to abandon, the alternative is to pivot the flagship to a migration whose target codebases test their data layer better. Candidates worth a Phase 0 of their own:

- Django 3.x → 4.x query API changes
- pytest 7 → 8 migration patterns
- mypy strict mode adoption (annotates uncovered surface, doesn't change runtime)
- httpx async migration (continues the work of `deprecated_api_requests_to_httpx` but for httpx 0.x → 1.0)

None of these have been investigated; Pivot B is a re-scoping conversation, not a recipe.

## What does NOT change

The Phase 0 code surface (Tasks 1 + 2 + 3 + the normalization fixup) is sound and reusable. The detector, the coverage reporter, the `testCovered` plumbing — they all work as specified. If Pivot A is chosen, the flag-only release uses every piece. If Pivot B is chosen, the coverage reporter is general-purpose and can be repurposed for any future detector that wants test-coverage signal.

### Notes / caveats

- New numbers are **byte-identical** to the prior Phase 0 run on every per-codebase bucket and every flag-reason count. The Tasks 3–6 class-attr fix is verified in code (24 unit tests in `tests/unit/analyze/detectors/python/sqlalchemy-query.test.ts` cover the `Model.query.<method>(...)` form across every safe and flag variant) but had nothing to detect in this corpus.
- Flask-AppBuilder uses higher-level abstractions (declarative views, generic interfaces) that wrap rather than expose ORM queries; the raw query sites it does contain are in `bin/` and `examples/` paths pytest never executes — same structural gap the prior run identified.
- sqlalchemy-utils is a utility library whose query sites live in `tests/` and `sqlalchemy_utils/` modules that the default `coverage run -m pytest` collection doesn't reach without a fixture-aware test config.
- The STOP verdict is **strengthened**, not weakened, by this re-trial: fix-with-no-effect ≠ broken-fix. The premise gap is the corpus, not the detector.
